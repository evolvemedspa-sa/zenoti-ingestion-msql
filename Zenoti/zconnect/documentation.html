zconnect

Python scripts that pull HyperConnect (formerly ZConnect) reporting data out of Zenoti and write it to CSV.

Two hosts, two credentials

Everything here talks to one of two hosts. They are not interchangeable — each rejects the other's credential.

HostAuth headerCredential fromServes
api.zenoti.com Authorization: apikey <KEY> ZENOTI_API_KEY ZConnect REST routes under /v1/zconnect/
hyperconnectapi.zenoti.com Authorization: Bearer <TOKEN> HC_TOKEN /features/v1/, /dashboard/, /recording/

Which script uses which credential

Script ZENOTI_API_KEY HC_TOKEN Live calls made to
events.py requirednot used api.zenoti.com only
usage_data.py requirednot used api.zenoti.com only
feedback_metrics.py requirednot used api.zenoti.com only
call_logs.py requiredrequired both — see note
agent_metrics.py requiredrequired both — see note
location_performance.py requiredrequired both — see note

Both means the script signs in twice, for different reasons:

  • ZENOTI_API_KEY is required even by the HyperConnect scripts. _client.py refuses to import without it — ZENOTI_API_KEY is missing. Add it to your .env file. — so a missing key breaks every script, including ones that never call api.zenoti.com for data. (The resolution: everything shares one module.)
  • agent_metrics.py calls list_centers() on api.zenoti.com on every run, to get center names and to iterate centers one at a time — that route takes a singular center_id.
  • call_logs.py and location_performance.py only reach the Zenoti host when --center-id is given as a code like BEL, which must be resolved to a UUID. Given a UUID, or nothing at all, they talk to the HyperConnect host alone.
The two credentials are not interchangeable The HC_TOKEN bearer also happens to work on api.zenoti.com — it opens /v1/reports, which the apikey is refused. But the apikey does not work on the HyperConnect host: seven header forms and a query parameter were all rejected with 401. HyperConnect has no login or refresh route, so HC_TOKEN must be pasted by hand and re-pasted when it expires.
HC_TOKEN expires It is a dashboard session token, not an API key, and the apikey cannot replace it. To refresh: open the HyperConnect dashboard, press F12 → Network → Fetch/XHR, pick any hcreports call, copy the value after Bearer from the authorization request header, and paste it into .env. Single-quote the value — it contains $ and |, which break .env parsing otherwise.

Quick start

Activate: .venv\Scripts\Activate.ps1
Run:      python zconnect\events.py

Run any script with no arguments and it fetches every center, for the date range in .env (or the last 7 days if unset), and writes a CSV named after the range.

Common behaviour

Flags every script shares

FlagMeaning
--center-idNarrow to one center. Accepts a UUID or a center code like BEL. Omit it and you get every center — that is the default, not an opt-in.
--start-date / --end-dateYYYY-MM-DD. Fall back to ZENOTI_START_DATE / ZENOTI_END_DATE, then to the last 7 days.
--csvOutput path. Each script has its own sensible default.
ZENOTI_CENTER_ID does not narrow anything It is deliberately ignored by the center resolver. With it set in .env, a bare run would otherwise fetch one center and look complete — exactly the silent-truncation failure worth avoiding. Only an explicit --center-id narrows.

Date windows are chunked automatically

Each route rejects a window wider than its cap, so scripts split longer ranges and stitch the results. You can always ask for any range.

RouteWidest window
ZConnect events10 days
ZConnect usage data32 days
ZConnect feedback metrics185 days
HyperConnect call logs31 days
HyperConnect dashboard routesno cap observed (365 days fine)

Failures are retried, then reported

Throttled responses (403 or 429 — Zenoti uses both) and hung connections are retried with exponential backoff before a script gives up. Tuning lives in .env: ZENOTI_MAX_RETRIES, ZENOTI_RETRY_BACKOFF, ZENOTI_REQUEST_DELAY.

events.py

GET /v1/zconnect/centers/{center_id}/events

Appointments, feedback, bot interactions and other centre activity, newest first.

Fields (18)

guest_id, guest_name, mobilephone, event_id, action_type, source, send_date, reference_id_1, reference_id_2, old_value, new_value, metadata, profile_image, centerid, center_name, category_type, unread, channel_medium

All 18 columns are always written, even when a field is blank on every row — the field list is held explicitly rather than inferred from what the API happened to return.

Flags

--filter feedbackNarrow to the feedback feed (category_type 5). Unrecognised values are ignored by the API.
--expand-metadataSpread the metadata JSON into metadata_<key> columns.
--sizeRecords per page (default 200).
--max-pagesPage cap per chunk (default 50). Prints a warning if it truncates.

The metadata field

metadata is a JSON string holding an array of objects, and its shape depends on category_type. Four have been observed:

  • a bare marker — {"ItemType": n}
  • a call record — guest_name, guest_phone_number, conference_name, outbound_recording, is_international
  • a guest/CRM block — InvoiceId, MobilePhone, GuestReferralCode, center address fields, Opt-OutKeyword
  • an appointment block — AppGroupId, StartTime, TreatmentList, AppCost

By default it is written through verbatim. With --expand-metadata each object becomes its own row with its keys spread as metadata_<key>, so an event carrying three objects produces three rows, distinguished by metadata_index. Expect a wide, sparse file — that is the honest shape of a polymorphic field.

python zconnect\events.py --start-date 2026-09-01 --end-date 2026-09-30 --expand-metadata
# -> zconnect_events_all_meta_2026-09-01_2026-09-30.csv

usage_data.py

GET /v1/zconnect/financial/usage_data?center_id=..&channel=..&start_date=..&end_date=..

Messaging usage per day for each center.

Fields (10)

date, total_sent_count, twoway_count, mms_count, notification_count, marketing_count, incoming_count, total_segments, outbound_segments, inbound_segments

Rows are tagged with center_id and center_name, which the response itself does not carry.

Flags

--channele.g. SMS. Omit for all. Only channels a center actually uses return data.
center_id is mandatory on this route Without it the API answers CT026. Because it cannot be sent as a list, the all-centers default is a loop — one request per center per chunk.

feedback_metrics.py

GET /v1/zconnect/centers/{center_id}/feedbacks/metrics

Review counts per day, per center.

Fields

date, total_reviews, total_replies, plus a nested ratings array which is flattened into rating_1_count … rating_5_count so the file stays one row per date. Rows are tagged with center_id and center_name.

call_logs.py

POST /features/v1/hcreports/call_logs

One row per call. The Agent Metrics and Location performance screens are aggregations of this same data, though the dedicated dashboard routes below supersede the rollups here for those two views.

Flags

--by rawDefault. One row per call.
--by agentRollup per agent: calls, made, received, analyzed, sentiment counts, average duration.
--by centerRollup per center.
--page-sizeCalls per page, max 200 (larger values silently clamp).

How the numbers map to the screen

Screen metricDerivation
callsevery row
calls madecall_type == 1 (outbound)
calls receivedcall_type == 0 (inbound)
calls analyzedsentiment is not None — not transcription_status
positive / negative / neutralthe sentiment value

call_type == 2 is neither made nor received — it is the bulk of the agent-less rows (voicebot / missed) and counts toward calls only.

Timestamps

The API sends timestamp as epoch milliseconds in UTC — 1792007181000 is 1792007181 seconds, i.e. 2026-10-14 19:46:21 UTC. A spreadsheet renders that as 1.79201E+12: unreadable, and wrong by seconds if the displayed text is copied back out.

So the raw pull replaces that column with two ISO text columns, which Excel leaves alone:

timestamp_utc        timestamp_local
2026-10-14 19:46:21  2026-10-14 15:46:21

Nothing is lost — timestamp_utc carries the same instant the integer did, and the pair sits in the position timestamp occupied. A value that will not parse keeps its original timestamp rather than becoming a guessed date.

The local column uses a -04:00 offset, which is where every centre in this org sits. Point this at another timezone and set HC_UTC_OFFSET to match. The rollups (--by agent / --by center) aggregate the timestamp away, so these columns appear on raw pulls only.

Center coverage With no --center-id this sends an empty center_ids list, which the route reads as "every center" — all 15 HyperConnect-active locations, including Scarsdale, NY. Scarsdale serves calls but is absent from /v1/centers, so filtering by that list would miss it.

agent_metrics.py

POST /dashboard/fetch_all_agent_data

The Agent Metrics screen: call totals, average rating, average time to answer, average call duration and sentiment, one row per agent per day. These columns cannot be derived from call logs — guest_rating is null on every call row and time-to-answer does not exist there.

Daily is not a flag: the request always sends day_wise: true. The client asked for day grain because the dashboards roll days up to a month or a fortnight themselves, and a windowed total cannot be split back into days.

Flags

--call-modeFilters which agents appear. Unset (the default) returns everything.
--call-modeAgents over a fortnight
unset / 2 / null73 — the default
159 — what the dashboard sends, i.e. the on-screen view
014

call_mode changes which agents appear, not their values — an agent present in both cuts reports the same numbers.

Date columns

start_date, end_date and date all carry the row's own day, not the window that was asked for — every row covers exactly one day. That keeps the table's key exact at day grain, so a lookback run rewrites the day instead of stacking a second overlapping window on top of it. An agent with no calls that day is simply absent from the pull.

Day-wise rows and the aggregate row do not agree exactly: over one fortnight the day-wise rows summed to 499 calls where the aggregate reported 495. The daily column is what the table holds.

Traps center_id is singular here — sending a list raises a DynamoDB ValidationException that reads like a server fault. Dates are YYYYMMDD integers: an ISO string dies with invalid literal for int() with base 10, and an epoch timestamp parses happily but matches nothing, returning an empty list rather than an error. A narrow window also returns nothing rather than erroring, so give it room.

This is the one script that walks the /v1/centers list rather than HyperConnect's, because it must call each center individually. Scarsdale, NY is absent from that list; it has returned 0 agents over a 365-day window, so nothing is currently lost.

location_performance.py

POST /dashboard/fetch_centers_performance

The Location performance screen: overall rating, flagged negative calls, SmartBot appointments and revenue, AI receptionist booking revenue and Google rating, one row per center per day.

This route has no day-wise switch — it answers per-center totals for whatever range it is given — so daily rows come from asking one day at a time: one call returns every center, so a seven-day lookback costs seven calls. Verified 2026-10-17: three days pulled one at a time and summed match the same three days asked for as one window, per additive field (negative calls 10 = 10, appointments 1 = 1). Averages do not add, and should not — each row carries its own day's overall_rating.

Flags

--sort-byoverall_rating (default), sb_revenue, total_negative_calls, sb_total_appointments, google_rating
--sort-orderdesc (default) or asc
--topKeep only the first N rows after sorting, per day.
--page-sizeRows per page, capped at 15 server-side.
--orgAlso pull the org-level KPI cards.
--timeseriesAlso pull the org call-volume chart.

start_date and end_date are both the row's own day, so a row reads the same however wide the window was and the table's key (center_id, start_date, end_date) stays exact at day grain.

The route's rollups lag, and the newest day is often missing because of it: on 2026-10-17 a pull covering Oct 16–17 returned nothing for both days, while agent_metrics already had Oct 16 — and the org call-volume chart agreed with this route, not with the agent one. So a deployed run can find T-1 empty and pick that day up on the next run instead. That is what the lookback is for, and an empty day is a no-op: the loader deletes only the keys it was handed, so a day with no rows leaves the day already in the table untouched.

Two extra routes on the same screen

FlagEndpointOutput columns
--org POST /dashboard/fetch_org_performance metric, curr, prev — active locations, Google rating, SmartBot revenue, AI receptionist revenue, negative calls flagged, plus flat call-category and feature counts
--timeseries POST /dashboard/fetch_org_level_call_volume_timeseries_plot date, incoming_calls, outgoing_calls, missed_calls
15 rows is the whole set, not a truncated page page_size clamps at 15 server-side, and that 15 is everything: the org reports exactly 15 active_locations, and this route returns those same 15. The next_token it returns is not a cursor — feeding it back returns an empty page, so it is ignored rather than looped over.

Note the date format here is the opposite of the agent routes: ISO strings, not YYYYMMDD integers. The two /dashboard handlers were written differently.

Shared client — _client.py

Import target for every script. Provides the session, retry logic, the date-chunking helper, the CSV writer, and both error conventions.

Helpers

Run python zconnect\_client.py for its self-check, or python zconnect\_client.py --centers to list center IDs.

Error conventions

What you seeWhat it means
CT028 with HTTP 200Empty result, not a failure. A range with no activity answers this instead of an empty list. Handled silently.
CT004 / CT026 / CT060 / CT061Real errors — invalid input, missing center, missing dates.
HTTP 403Usually throttling, not permission. The same request succeeds moments later, so it is retried.
HTTP 401 on HyperConnectHC_TOKEN expired — paste a fresh one.
403 "Invalid key=value pair"That HyperConnect route does not exist.
{"statusCode": 500} with HTTP 200Some HyperConnect handlers report failures this way.
